# Аудит SR Lux Premium (srlux.uz) — бриф для Claude Code

## Кто мы и зачем этот файл
Пользователь (Суннат) ведёт SR Lux (интернет-магазин отопительного оборудования,
Узбекистан) в основном сам, включая маркетинг и техническую сторону. Этот бриф
писала другая сессия Claude Code (на компьютере пользователя), которая только что
разобралась с Google Search Console для этого сайта и обнаружила серьёзную проблему.
Тебе (Claude Code на этом сервере) нужно провести прицельный технический аудит —
не "аудит всего подряд", а конкретно по пунктам ниже, с приоритетом на пункт 1.

## Контекст: что уже известно (не переоткрывай заново)
- Стек: FastAPI + SQLAlchemy async + Postgres (backend), React+TS+Vite+Tailwind (frontend),
  nginx reverse proxy, всё в Docker (`srlux-api`, `srlux-web`, `srlux-nginx`, `srlux-postgres`, `srlux-redis`).
- В корне проекта уже есть `CLAUDE.md` с историей проекta и известными граблями — прочитай его первым.
- Google Search Console (подключён впервые 2026-07-19) показал: почти нулевую видимость в поиске
  (3 клика / 32 показа за 3 месяца, только по брендовым запросам), и всего 2 из 106 страниц sitemap
  реально проиндексированы Google спустя неделю после подачи sitemap.
- Уже выяснено: `frontend/src/lib/seo.ts` устанавливает `document.title`, meta-теги и JSON-LD
  **через JS на клиенте** (вызывается из компонентов страниц через useEffect, судя по всему).
  Это значит, что при первом (не-JS) проходе краулера все страницы отдают ОДИНАКОВЫЙ статический
  `<title>`/`<meta description>` из `index.html`, а уникальные per-product данные видны только
  после полного рендера React — что резко замедляет/осложняет индексацию у Google и делает её
  вообще невозможной для менее мощных краулеров (Bing, соцсети при шаринге ссылок).

## Задача 1 (главный приоритет): подтвердить и решить проблему SEO-рендеринга
1. Подтверди гипотезу фактически: сравни, что реально возвращает сервер на `curl -s https://srlux.uz/model/<любой-код>`
   (сырой HTML без JS) против того, что видно в браузере после рендера — конкретно `<title>`, `<meta name="description">`,
   `<script type="application/ld+json">`. Покажи разницу explicitly.
2. Предложи и оцени 2-3 реалистичных варианта фикса для этого стека (Vite+React SPA, без миграции на Next.js —
   это будет слишком большая переделка), например:
   - Пре-рендеринг статических HTML-снапшотов для всех /model/<code> страниц в момент ERP-синка
     (раз в 30 минут уже гоняется `erp_sync_dolibarr.py` — логично туда же добавить генерацию
     `<title>`/`<meta>`/`<jsonld>` в статические HTML-файлы или через отдельный маленький SSR-эндпоинт).
   - Middleware в FastAPI/nginx, который отдаёт краулерам (по User-Agent) пре-рендеренную версию
     через headless Chromium (аналогично тому, что уже есть в `backend/catalog_pdf.py` — там уже
     используется playwright для рендера PDF, значит headless-браузер в стеке уже есть и можно
     переиспользовать библиотеку).
   - Минимальный вариант: nginx отдаёт разный `index.html` для ботов (по User-Agent) с сервер-сайд
     подставленными title/description/og:image через простой Jinja2-шаблон в FastAPI, без полного SSR.
   Взвесь трудозатраты/риски каждого и дай рекомендацию — какой вариант внедрить первым.
3. Не внедряй фикс молча — опиши рекомендованный план в отчёте, дай пользователю выбрать, ЕСЛИ
   это требует архитектурных решений. Мелкие/очевидные правки (например добавить недостающие
   meta-теги в статический `index.html`) можно сделать сразу.

## Задача 2: незакоммиченные изменения — большой риск потери работы
`git status` показывает 28 изменённых файлов (backend и frontend), ~2700 добавленных строк,
последний коммит — 19 дней назад (2026-07-05). Это реальный риск: если что-то случится с диском
или кто-то по ошибке сделает `git checkout .`, все эти изменения пропадут.
- Просмотри `git diff` по каждому файлу, разберись что именно менялось (особенно `ModelPage.tsx`,
  где +658/-462 строк — судя по всему, это переписывание страницы товара).
- Сгруппируй изменения по смыслу и закоммить их отдельными осмысленными коммитами
  (не одним огромным коммитом "wip"). Если что-то выглядит как незаконченный эксперимент —
  явно укажи это в отчёте вместо того, чтобы коммитить вслепую.
- Не пуш и не форсируй ничего без явного указания — просто закоммить локально достаточно
  для защиты от потери данных, пуш можно оставить пользователю.

## Задача 3: беглая проверка безопасности новых изменений
В `CLAUDE.md` описан уже пройденный OWASP-аудит (коммит `a476cd1`). Но с тех пор (28 незакоммиченных
файлов) менялись `backend/main.py`, `backend/models.py`, `backend/routers/models.py`,
`backend/routers/orders.py`, `nginx/nginx.conf` — то есть как раз файлы, где раньше были
security-фиксы. Проверь, не отменили ли эти правки что-то из уже сделанного (CORS, rate-limit,
CSP-заголовки, дефолтные секреты, генерик 401). Если да — явно укажи, что именно откатилось.
