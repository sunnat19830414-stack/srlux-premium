# SR Lux Premium — CLAUDE.md

## 1. Что это и зачем

E-commerce платформа для **SR Lux** — интернет-магазин отопительного оборудования
(радиаторы, конвекторы, котлы, полотенцесушители, климат-контроль) в Ташкенте,
Узбекистан. Ведёт бизнес и весь маркетинг практически в одиночку пользователь
(Суннат). Сайт — витрина каталога с ценами/наличием в реальном времени и
оформлением заказа; источник истины по товарам, ценам и остаткам — ERP **Dolibarr**
(отдельный сервер bollente.uz), синхронизация в одну сторону (Dolibarr → сайт).

Продакшен: **srlux.uz**, сервер доступен как `root@srlux.uz`.
Репозиторий: `github.com/sunnat19830414-stack/srlux-premium`, рабочая ветка
`claude/test-coverage-analysis-qKQZ7` (ещё не смёржена в main).

## 2. Архитектура и стек

- **Backend**: FastAPI + SQLAlchemy 2.0 (async) + PostgreSQL. Роутеры в
  `backend/routers/` (`products.py`, `admin.py`, ...), бизнес-логика запросов — в
  `backend/crud.py`, ORM-модели — `backend/models.py`, Pydantic-схемы — `backend/schemas.py`.
- **Frontend**: React + TypeScript + Vite + Tailwind, SPA (client-side routing),
  собирается через `serve -s dist` (полный SPA-fallback на любой путь).
- **nginx** — реверс-прокси и по совместительству отдаёт **статические SEO-снапшоты**
  (см. раздел 4) в обход SPA для отдельных `location` (товары/категории/статика).
- **Синхронизация с Dolibarr**: `backend/erp_sync_dolibarr.py`, крон каждые 30 мин
  (`docker exec srlux-api python erp_sync_dolibarr.py`, лог — `/var/log/srlux_sync.log`).
  Тянет товары+категории из Dolibarr REST API, пишет в Postgres, попутно
  генерирует статические SEO-снапшоты (см. ниже).
- **Docker Compose**, контейнеры: `srlux-api`, `srlux-web`, `srlux-nginx`,
  `srlux-postgres`, `srlux-redis`. Backend/frontend код **встроен в образ при сборке**,
  не bind-mount — после правки `.py`/`.tsx` файлов нужен
  `docker compose build <service> && docker compose up -d --no-deps <service>`,
  простого редактирования на хосте недостаточно. Из bind-mount — только
  `./static/uploads:/app/uploads` (сюда же кладутся SEO-снапшоты) и `nginx.conf`
  (можно просто `docker exec srlux-nginx nginx -s reload`, без пересборки).
- **Уведомления о заказах** — в Telegram.
- Товарный каталог не плоский список: **архитектура "модель → варианты"**
  (`parent_model` группирует SKU-варианты по цвету/секциям/размеру в одну карточку модели).

## 3. Текущий статус

**Готово и работает:**
- Каталог с человекочитаемыми URL категорий (`/catalog/<slug>`, транслитерация
  кириллицы), обратная совместимость со старыми `?cat=<id>` через клиентский редирект.
- Admin-панель: CRUD товаров/категорий, загрузка+сжатие фото, генерация PDF-каталога
  по нескольким категориям, ручное создание товаров с галереей.
- Статические SEO-снапшоты для `/model/<code>`, `/catalog/<slug>` (текущий URL,
  50 категорий) + легаси `/catalog?cat=<id>` (канонизируется на новый slug-URL,
  не на себя) и статических страниц (`/`, `/about`, `/contacts`, `/delivery`,
  `/returns`) — генерируются при каждом синке, отдаются nginx в обход SPA.
  С 2026-10-08 в снимках есть и видимое содержимое внутри `#root` (H1, описание,
  характеристики, таблица вариантов, «хлебные крошки», ссылки главная → категория →
  модель); React (`createRoot`) заменяет его при загрузке.
- `sitemap.xml` с `<lastmod>` из `static/uploads/sitemap-lastmod.json` — дата меняется
  только при изменении «стабильного» содержимого страницы (не цены/остатка).
- Описания моделей целиком (не первого варианта) — `backend/model_descriptions.json`
  (`{"<код>": {"ru", "uz"}}`), пока только JDC22.
- Синк остатков с Dolibarr — с 2026-08-19 запрашивает `includestockdata=1`,
  раньше отдавал 0/устаревшее значение для ~45% товаров (см. раздел 4).
- USD/UZS переключатель цены, YML-фид для Яндекс.Маркета, GA4 purchase-tracking.

**В процессе / известные хвосты:**
- 12+ товаров в Dolibarr помечены `status=0` ("не для продажи") при этом с реальным
  остатком на складе — это не баг сайта, а вопрос данных в самом Dolibarr, ждёт
  решения пользователя (реактивировать или оставить).
- С 2026-10-08 сервер работает с ветки **`main`** (старая
  `claude/test-coverage-analysis-qKQZ7` слита и удалена). Код backend «запечён»
  в образ `srlux-api` (не примонтирован): правки без пересборки — `docker cp` +
  `docker restart srlux-api`, и тот же файл — в репозиторий. Параллельных сессий
  может быть несколько — сверяйте `git log`/`git status` перед началом работы.
- `.bak*`-файлы в `backend/` — снапшоты старых версий crud.py/main.py/etc, можно
  чистить, если не нужны для истории отладки.

## 4. Ключевые решения и почему

### SPA + client-side SEO-теги — несовместимо с индексацией, решено статическими снапшотами
`frontend/src/lib/seo.ts` ставит `<title>`/meta/JSON-LD **через JS в браузере**
(`useEffect` на страницах). Гуглобот при первом (нерендеренном) проходе видел
одинаковый generic `<title>` из `index.html` на всех страницах — это почти
остановило индексацию (Search Console: 3 клика/32 показа за 3 месяца на момент
диагностики 2026-07-19). Мигрировать на Next.js ради SSR — слишком большая
переделка. Решение: `erp_sync_dolibarr.py` при каждом синке рендерит готовый
`index.html` с подставленными title/description/canonical/JSON-LD в файл на диске
(`generate_model_snapshots`/`generate_category_snapshots`/`generate_static_snapshots`,
пишут в `/app/uploads/{model,category,static}-snapshots/`), а nginx отдаёт эти
файлы вместо SPA-шелла по точному `location` (либо по `$arg_cat` для query-string
маршрутов, т.к. `location` не матчит query string) — с фоллбэком на обычный SPA
(`@spa`), если снапшота ещё нет. React использует `createRoot` (не `hydrateRoot`),
поэтому просто перерисовывает `#root` с нуля — mismatch-рисков нет.
**Грабля 2026-08-19**: у категорий канонический тег в снапшоте по умолчанию был
`https://srlux.uz/` (голый домен) вместо адреса самой категории — 59 страниц
`/catalog?cat=N` Google пометил как "неканонические варианты" и не индексировал.
Причина: `generate_category_snapshots` изначально не существовал вообще, категории
никогда не попадали под этот механизм. Фикс — добавлена сама функция + nginx-правило.

**Грабля 2026-08-31 (повтор того же класса бага, другой триггер)**: фронтенд
перешёл на человекочитаемые `/catalog/<slug>` (commit `3cb57e4`, 2026-08-06), но
`generate_category_snapshots()` и nginx продолжали знать только про старый
`?cat=<id>`. Новый URL не матчился ни одним `location`, значит Googlebot получал
сырой SPA-шелл — снова title/canonical главной страницы, снова 62 страницы
не индексировались. **Урок**: при любой смене схемы URL для раздела, у которого
уже есть статический SEO-снапшот, сразу проверять, попадает ли НОВЫЙ URL под
существующий nginx `location` — само по себе наличие снапшот-системы не защищает
от этого класса бага, если её не обновить вместе с роутингом. Фикс — снапшоты
теперь пишутся под оба URL (`{slug}.html` self-canonical, `{cat_id}.html`
canonical → на slug-URL), добавлен `location ~ ^/catalog/([A-Za-z0-9._-]+)$`.

### Dolibarr API — не доверять полям без проверки
- `stock_reel` из списка `/products` **не гарантированно актуален** — денормализованное
  поле на строке товара, не всегда синхронизировано с реальными движениями склада:
  null у ~90 из 345 товаров, у ~66 ещё — просто неверное число (то завышено, то
  занижено). Нужен параметр `includestockdata=1` — тогда Dolibarr считает остаток
  "живьём" из журнала движений. Без этого сайт показывал "нет в наличии" для товаров
  с реальным остатком на складе (обнаружено 2026-08-19 по жалобе, что реально
  есть на складе — JD3015 антрацит/белый, 7 и 8 шт).
- `price_base_type` — это `"TTC"/"HT"`, НЕ код валюты.
- Цена иногда лежит только в `multiprices_ttc[level]`, если `price_ttc == 0` — нужен fallback.
- `category_ids` товара в Dolibarr часто пуст — категории приходится подтягивать
  отдельным запросом `GET /categories?type=product&object_id={pid}` на каждый товар.
- Товары с `status=0` в Dolibarr всё равно приходят в ответе API несмотря на
  фильтр `status=1` в запросе — фильтруются на нашей стороне явно.
- Фото из Dolibarr периодически ненадёжны (то нет данных в `photos`, то вообще левые
  фото не по теме) — есть флаг `image_manual`, защищающий вручную загруженные фото
  от перезаписи синком.

### Category tile images — ручной override не проверяется на существование файла
`frontend/src/lib/categoryTiles.ts` содержит `TILE_IMAGE_OVERRIDE` — ручной список
"эта категория → вот эта картинка", когда авто-подбор обложки из товаров даёт не тот
результат (например, одна и та же модель продаётся и как вертикальный, и как
горизонтальный радиатор — авто-фото могло не совпадать с ориентацией). Опечатка в
одной из строк (`dol_2301.jpg` вместо реального `dol_2301_5fea0d5766.jpg` — Dolibarr
добавляет хеш к загруженным файлам) держала плитку "Плоские 68×12" пустой до
2026-08-19. При добавлении новых override-записей — всегда проверять файл на диске,
опечатка не даёт ошибки, просто тихо не показывает картинку.

### AI-обработка фото товаров (`tools/smart_photo_processor.py`)
После серии неудачных попыток с Claid.AI (эндпоинты/форматы менялись 7 раз подряд,
плюс сложности с публичным URL для загрузки фото) — заброшено. Основной путь —
**Photoroom API**, с fallback на локальный numpy-recolor, если API недоступен.
Если понадобится AI-фотообработка снова — начинать сразу с Photoroom.

### Прочее
- Docker/nginx: `resolver 127.0.0.11` + ленивый резолвинг хоста через `set $var` в
  `proxy_pass` — иначе nginx падал при старте, если api/web ещё не в Docker DNS.
- Безопасность: OWASP-проход — убраны дефолтные секреты, rate-limit на `/api/admin/`,
  CORS сужен, CSP/HSTS/Referrer-Policy заголовки (в `server{443}`, не в `http{}` —
  не сработало надёжно на уровне http-блока), DOMPurify на HTML-описания из Dolibarr.
- `npm ci` падал в Docker-сборке → заменено на `npm install`. Сжатие — силами nginx,
  не `GZIPMiddleware` в приложении.
